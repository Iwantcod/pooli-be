# 일별 동기화 배치 시스템 정리 문서

본 문서는 일별 트래픽 배치 시스템의 구성 및 동작 절차를 명사 종결형 개조식으로 요약한 가이드입니다.

```mermaid
sequenceDiagram
autonumber
participant Scheduler as 모든 서버
participant Redis as Redis
participant Manager as Manager (1대)
participant Worker as Worker (나머지 + Manager)
participant DB as MySQL

    Scheduler->>Redis: 03:00 KST Manager 락 획득 시도
    Redis-->>Manager: 락 획득 성공 (Manager 선출)
    Redis-->>Worker: 락 획득 실패 (Worker 대기)
    
    rect rgb(240, 248, 255)
        note right of Manager: 1. Target Insert 절차 (대상 준비)
        Manager->>DB: 메타데이터 생성 및 Target Row 일괄 적재
        Manager->>DB: 동기화 배치 상태 "RUNNING" 전환
    end

    Manager-->>Worker: Manager도 세팅 완료 후 Worker로 합류
    
    rect rgb(240, 255, 240)
        note right of Worker: 2. Usage Sync 절차 (다중 워커 병렬 동기화)
        loop 잔여 타겟 소진 시까지 반복
            Worker->>DB: 100건 할당/선점 (SKIP LOCKED)
            Worker->>Redis: 대상 유저의 사용량 스냅샷 조회
            Worker->>DB: [단일 트랜잭션] 사용량 적재 & 상태 완료 갱신
        end
    end
    
    Worker->>DB: 처리할 타겟이 없으면 최종 "COMPLETED" 갱신
```

## 1. 동기화 배치 절차 구성 요소
* **Scheduler**: 매일 03:00 KST 전 노드 배치 트리거
* **Manager 노드**: Redis 분산 락 획득 기반 단일 리더 선출, 메타데이터 생성 및 Target Insert 배치 수행
* **Worker 노드**: Manager 외 서버 및 작업 완료 Manager 서버, Redis-DB 동기화 처리를 위한 Claim 루프 병렬 실행
* **Redis**: Manager 선출용 분산 락 및 일별 트래픽 사용량 원본 데이터 저장소
* **MySQL**: 메타데이터(`LINE_DAILY_BATCH_JOB`), 배치 대상(`LINE_DAILY_BATCH_TARGET`), 최종 사용량 데이터 영속화 저장소

## 2. Manager 노드 선별 과정
* **시점**: 매일 03:00 KST
* **대상**: `traffic`, `local` 프로파일 구동 전 서버
* **방식**: 동일 전일 `usage_date` 기준 Redis Manager Lock 1회 획득 시도 (재시도 없음)
* **분기**:
    * **성공 (1대)**: Manager 선출, 메타데이터 생성 및 Target Insert 배치 수행, 완료 후 Worker 시작 감지 돌입
    * **실패 (나머지)**: Manager 작업 스킵, 즉시 해당 `usage_date` Worker 시작 감지(Polling) 돌입

```mermaid
sequenceDiagram
    autonumber
    participant ServerA as 서버 A
    participant ServerB as 서버 B (기타 노드들)
    participant Redis as Redis
    participant DB as MySQL

    Note over ServerA, ServerB: 매일 03:00 KST (모든 서버 스케줄러 동시 가동)
    
    ServerA->>Redis: Manager 락 획득 시도 (전일 usage_date 키 사용)
    ServerB->>Redis: Manager 락 획득 시도 (전일 usage_date 키 사용)
    
    Redis-->>ServerA: 락 획득 성공 (True 반환)
    Redis-->>ServerB: 락 획득 실패 (False 반환 - 재시도 안 함)

    rect rgb(255, 245, 245)
        note right of ServerA: [Manager 역할 확정]
        ServerA->>DB: 배치 메타데이터 생성 및 Target Insert 시작
    end

    rect rgb(240, 248, 255)
        note right of ServerB: [Worker 역할 확정]
        ServerB-->>ServerB: Manager 전용 로직 즉시 스킵
        ServerB->>DB: 동기화 배치가 "RUNNING" 될 때까지 감지(Polling) 시작
    end
    
    Note over ServerA: Target Insert 무사히 완료 시
    ServerA->>DB: 동기화 배치 상태 "RUNNING"으로 전환
    ServerA-->>ServerA: Manager 역할 종료, 자신도 Worker 감지 절차로 진입
```

## 3. Target Insert Batch 절차
### 신규 시작 절차
* **메타데이터 생성**: Manager 노드가 `LINE_DAILY_TARGET_INSERT_BATCH` (RUNNING) 및 `LINE_DAILY_USAGE_SYNC_BATCH` (PENDING) 생성
* **타겟 적재**: 전일 `usage_date` 기준 `LINE` 테이블 순회, 청크(1,000건) 단위 `INSERT IGNORE`로 `LINE_DAILY_BATCH_TARGET` 적재
* **상태 전환**: Target Insert 완료 후 Job 카운트 갱신 및 `COMPLETED` 전환, 이후 Usage Sync Batch `RUNNING` 전환

```mermaid
sequenceDiagram
    autonumber
    participant Manager as Manager 노드
    participant Job as 메타데이터 테이블<br/>(BATCH_JOB)
    participant Line as 가입자 테이블<br/>(LINE)
    participant Target as 배치 타겟 테이블<br/>(BATCH_TARGET)

    Note over Manager: Manager 선출 직후 Target Insert 개시
    
    Manager->>Job: Insert 배치 및 Sync 배치 메타데이터 확인
    
    alt 완전히 처음 시작하는 경우 (신규)
        Manager->>Job: Insert 배치 "RUNNING", Sync 배치 "PENDING"으로 생성
        Manager->>Line: 처음부터 순차적으로 조회 준비
    else 장애/중단 후 다시 시도하는 경우 (재개)
        Manager->>Target: 전일(usage_date) 기준으로 가장 마지막에 넣은 최대 line_id 조회
        Manager->>Line: 조회된 최대 line_id 다음부터 조회 준비 (처음부터 다시 스캔 안 함)
    end

    rect rgb(240, 248, 255)
        note right of Manager: 청크(Chunk) 기반 대상 적재 반복
        loop 가입자(LINE) 데이터 소진 시까지
            Manager->>Line: Chunk 단위(1,000건)로 가입자 조회
            Manager->>Target: "INSERT IGNORE" 방식으로 타겟 1,000건 밀어넣기
            Note over Target: 💡 INSERT IGNORE를 통해 이미 들어간 타겟의<br/>기존 상태나 재시도 횟수는 덮어쓰지 않고 보존됨
        end
    end

    Manager->>Target: 실제로 적재 완료된 총 타겟 건수 재확인
    Manager->>Job: Target Insert 배치를 "COMPLETED"로 갱신
    Manager->>Job: 대기 중이던 Usage Sync 배치를 "RUNNING"으로 전환
    Note over Job, Target: (이제 대기하던 Worker들이 일제히 데이터를 가져가기 시작함)
```

### 중단 시 재개 절차
* **복구 주체**: Worker 개입 없이 Manager 배치의 명시적 재시도를 통해서만 복구 수행
* **재개 지점**: `LINE_DAILY_BATCH_TARGET`의 해당 `usage_date` 기준 최대 `line_id` 조회 후 이후 시점부터 청크 이어붙이기 (Chunk Insert)
* **데이터 보존**: `INSERT IGNORE` 유지로 기존 타겟의 처리 상태 및 재시도 횟수 보존

```mermaid
sequenceDiagram
    autonumber
    participant Manager as Manager 노드<br/>(배치 재시도 주체)
    participant Job as 메타데이터 테이블<br/>(BATCH_JOB)
    participant Target as 배치 타겟 테이블<br/>(BATCH_TARGET)
    participant Line as 가입자 테이블<br/>(LINE)

    Note over Manager: 장애 발생 후, Manager 배치의 명시적 재시도 진입
    
    Manager->>Job: Target Insert 배치의 상태 조회 (미완료 혹은 실패 확인)
    
    rect rgb(255, 245, 245)
        note right of Manager: 1. 재개 시작점(이어달리기) 탐색
        Manager->>Target: 해당 일자(usage_date) 기준으로 가장 큰 line_id (MAX) 조회
        Target-->>Manager: 중단 직전에 마지막으로 들어간 line_id 반환 (예: 50,000)
    end
    
    Manager->>Line: DB 전체 스캔을 건너뛰고, line_id > 50,000 조건으로 조회 준비
    
    rect rgb(240, 248, 255)
        note right of Manager: 2. 끊긴 지점부터 Chunk 적재 이어서 진행
        loop 남은 LINE 데이터가 소진될 때까지
            Manager->>Line: Chunk 단위 (1,000건) 가입자 데이터 조회
            Manager->>Target: "INSERT IGNORE" 방식으로 1,000건씩 적재
            Note over Target: 💡 INSERT IGNORE의 강력한 이점:<br/>기존 타겟과 겹쳐도 에러가 나지 않으며,<br/>기존 타겟의 실패/시도 횟수나 현재 상태를 절대 덮어쓰지 않고 보존함
        end
    end

    Manager->>Target: 재개가 모두 끝나면, 총 생성된 타겟 개수 집계
    Manager->>Job: Target Insert 배치 메타데이터를 "COMPLETED"로 최종 전환
    Manager->>Job: 멈춰 있던 Usage Sync 배치를 "RUNNING"으로 전환하여 Worker들 호출
```

## 4. 동기화 배치 절차 (Usage Sync Batch)
### 신규 시작 절차
* **시작 대기**: Worker 노드들은 해당 `usage_date` Job이 `RUNNING` 상태가 될 때까지 `1초 + jitter` 간격 대기
* **타겟 선점**: `RUNNING` 전환 시 MySQL `SELECT ... FOR UPDATE SKIP LOCKED` 구문으로 PENDING, RETRYABLE, Lease Timeout(1분) 초과 PROCESSING 대상 청크 단위(100건) 선점 후 즉시 락 해제
* **데이터 조회**: 선점 타겟 기준 Redis 3종 Key 조회
* **동기화 처리**: 단일 MySQL 트랜잭션 내에서 사용량 테이블 Insert, 대상 Row Terminal(DONE/SKIPPED 등) 전환, Job 메타데이터 성공 카운트 증가 동시 수행
* **완료 처리**: 잔여 선점 타겟 소진 시 미완료 Row 재확인, 전건 처리 완료 시 Job `COMPLETED` 상태 CAS 갱신

```mermaid
sequenceDiagram
    autonumber
    participant Scheduler as Worker 노드
    participant Job as 메타데이터 테이블<br/>(BATCH_JOB)
    participant Target as 타겟 테이블<br/>(BATCH_TARGET)
    participant Redis as Redis 스냅샷
    participant DB as 사용량 적재 DB

    Note over Scheduler, Job: Manager의 Target Insert가 완전히 끝나면 자동 감지
    Scheduler->>Job: 해당 일자의 배치 상태 주기적 감지 (1초 + jitter 간격)
    Job-->>Scheduler: 상태 "RUNNING" 반환 시 동기화 작업 돌입
        
    rect rgb(240, 255, 240)
        note right of Scheduler: 동기화 병렬 처리 루프 (여러 Worker 동시 수행)
        loop 처리할 타겟이 0건이 될 때까지 무한 반복
            Scheduler->>Target: 100건 할당 및 선점 (SELECT ... FOR UPDATE SKIP LOCKED)
            Scheduler->>Redis: 할당받은 유저의 3종(총량, 앱별, 공유풀) 사용량 데이터 조회
            
            rect rgb(255, 250, 240)
                note right of Scheduler: [안전한 단일 MySQL 트랜잭션]
                Scheduler->>DB: 존재하는 사용량만 골라서 DB에 Insert
                Scheduler->>Target: 타겟 상태 변경 (DONE / SKIPPED / RETRYABLE 등)
                Scheduler->>Job: 메타데이터 카운트(성공 건수 등) 1 증가
            end
        end
    end

    Scheduler->>Target: 선점 가능한 잔여 미완료 타겟이 없는지 최종 확인
    Scheduler->>Job: 동기화 배치를 "COMPLETED" 상태로 갱신 (CAS 연산)
```

### 중단 시 재개 절차
* **재개 방식**: 서버 기동 시 자동 감지 불가, 명시적 관리자 API 호출 기반 제어
* **기존 RUNNING 상태 재개**:
    * API: `POST /api/admin/traffic/batches/daily-usage-sync/{usageDate}/resume`
    * 동작: 잔여 PENDING/PROCESSING/RETRYABLE 타겟 대상 Worker 스케줄러 재가동
* **FAILED/ABANDONED 상태 재처리 (Rerun)**:
    * API: `POST /api/admin/traffic/batches/daily-usage-sync/{usageDate}/rerun`
    * 동작: 기존 FAILED 타겟 수 기반 신규 `LINE_DAILY_USAGE_SYNC_BATCH` (RUNNING) 메타데이터 생성
    * 동작: 기존 FAILED 타겟 `RETRYABLE` 롤백 후 재처리 (DONE/SKIPPED 안전 무시)

```mermaid
sequenceDiagram
    autonumber
    participant Admin as 관리자 (Admin API)
    participant Scheduler as Worker 노드
    participant Job as 메타데이터 테이블<br/>(BATCH_JOB)
    participant Target as 타겟 테이블<br/>(BATCH_TARGET)
    
    Note over Admin, Job: 서버 다운 등 예기치 않은 중단/실패 발생 시

    alt 기존 RUNNING 상태가 유지된 경우 (/resume)
        Admin->>Scheduler: /resume API 명시적 호출
        Scheduler->>Job: 배치가 여전히 RUNNING인지 확인 후 즉각 스케줄러 속행
        
    else 한도 초과 등으로 완전히 실패한 경우 (/rerun)
        Note over Admin, Job: 상태가 FAILED 거나 ABANDONED 일 때
        Admin->>Job: /rerun API 명시적 호출
        Job->>Job: FAILED 개수 기반 [새로운 RUNNING 메타데이터] 신규 생성
        Job->>Target: 완전히 실패했던 타겟들만 "RETRYABLE"로 일괄 상태 롤백
        Job-->>Scheduler: 재처리 준비 완료, Worker 스케줄러 강제 가동
    end

    rect rgb(240, 255, 240)
        note right of Scheduler: 동기화 병렬 처리 루프 복귀
        loop 잔여 타겟 소진 시까지 (기존 로직과 동일)
            Scheduler->>Target: 타겟 할당/선점 (SKIP LOCKED)
            Note right of Target: 💡 서버가 죽으면서 방치된 타겟(Lease Timeout 1분 경과)과<br/>API를 통해 롤백된 타겟들을 빈틈없이 낚아챔
            Scheduler->>Scheduler: Redis 조회 및 DB 반영 처리 (단일 트랜잭션)
        end
    end
    
    Scheduler->>Job: 남은 재개/재처리 대상이 없으면 "COMPLETED" 최종 전환
```

## 5. 활용 Redis Key 목록
* **일별 총 사용량**: `pooli:daily_total_usage:{lineId}:{yyyymmdd}`
* **일별 앱 사용량**: `pooli:daily_app_usage:{lineId}:{yyyymmdd}` (Hash - 필드: `app:{appId}:individual`, `app:{appId}:shared`, `app:{appId}:qos`)
* **일별 공유풀 사용량**: `pooli:daily_shared_usage:{lineId}:{yyyymmdd}` (Hash - 필드: `usage_amount`, `family_id`)

## 6. 배치 제약조건
* **기술 스택**: Spring Batch, Redis Pub/Sub, Redis Streams 사용 불가
* **정합성 기준**: 순수 MySQL Lock 매커니즘(`SKIP LOCKED`)
* **적재 원칙**: 데이터베이스 Insert-only 기반, 중복 키 삽입 시도는 갱신이 아닌 실패 시그널로 간주
* **타임아웃**: Worker 선점 후 1분 경과 시 Lease Timeout 처리 (타 Worker 강제 재할당 대상)
* **실행 순서**: Target Insert 완전 종료 후 Usage Sync Worker 진입 강제
* **메타데이터 식별**: `LINE_DAILY_BATCH_TARGET` 내 `batch_job_id` 미포함, `usage_date` 기반 집합 식별

## 7. 배치 기능 요구사항
* **스냅샷 적재**: Redis 3종 Key 조회 후 3개 목적 DB(`DAILY_TOTAL_DATA`, `DAILY_APP_TOTAL_DATA`, `FAMILY_SHARED_USAGE_DAILY`)로 분할 저장
* **부분 상태(Partial) 처리**: 일부 Key만 존재 시 해당 데이터만 Insert 후 `DONE`, 전체 누락 시 Insert 생략 후 `SKIPPED` 처리
* **재시도**: 인프라 등 일시적 장애 시 최대 10회 `RETRYABLE` 처리, 한도 초과 및 복구 불가 오류는 `FAILED` 마킹

## 8. 배치 비기능 요구사항
* **멱등성 및 원자성**:
    * Target Insert: `INSERT IGNORE` 기반 중복 생성 방어
    * DB 동기화: DB Insert, 타겟 상태 갱신, Job 카운트 증가를 묶은 단일 MySQL 트랜잭션 사용으로 부분 실패 원천 차단
* **스레드 경합 방지**: TaskScheduler `pool.size` 2 확장으로 Manager Cron(03:00)과 Worker Polling 주기 간 병목 해소
* **모니터링**: Micrometer 메트릭(`batch_daily_usage_sync_failed_count` 등) 연동을 통한 Prometheus 수집 지원
* **알람 연동**: 데드라인(06:00) 초과 또는 `failed_count > 0` 발생 시 Discord 알림 발송 환경 구성
