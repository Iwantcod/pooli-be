## 1. 배치 실행 시간표 및 Deadline

| 항목 | 값 |
|---|---|
| 시작 시각 | 매일 03:00 KST |
| 완료 기한 | 매일 **06:00 KST** |
| 허용 처리 시간 | 최대 3시간 |
| 시작 트리거 | 모든 `traffic` / `local` 프로파일 서버의 `@Scheduled` cron |

06:00 KST 이전에 `LINE_DAILY_USAGE_SYNC_BATCH.status = COMPLETED`로 전환되어야 정상 완료로 간주한다.

## 3. 운영자 알림

### 3.1 알림 경로

```
Spring 앱 (Micrometer Gauge)
  → Prometheus (metric scraping)
    → AlertManager (Docker 컨테이너)
      → Discord 웹훅
```

### 3.2 노출 Metric 목록

Spring 앱이 아래 metric을 Micrometer Gauge로 노출한다.

| Metric 이름 | 설명 |
|---|---|
| `batch_daily_usage_sync_failed_count` | 현재 RUNNING usage sync batch의 `failed_count` |
| `batch_daily_usage_sync_status` | 현재 usage sync batch의 status 코드 |
| `batch_daily_usage_sync_run_duration_seconds` | RUNNING batch의 경과 시간(초) |

metric 수집은 DB 조회 기반 주기적 collector로 구현한다.  
RUNNING batch가 없을 때는 metric을 노출하지 않거나 기본값(0)으로 둔다.

### 3.3 Alert Rule 정의

| Alert 이름 | 조건 | 의미 | Discord 알림 |
|---|---|---|---|
| `DailyUsageSyncFailedTarget` | `batch_daily_usage_sync_failed_count > 0` | target row 처리 실패 발생 | 즉시 |
| `DailyUsageSyncDeadlineExceeded` | `batch_daily_usage_sync_run_duration_seconds > 10800` | 3시간 이내 미완료 (06:00 초과) | 즉시 |

> AlertManager rule 설정은 Docker 인프라 레벨에서 관리한다. Spring 앱은 metric 노출만 담당한다.

## 4. Admin API 구성

### 4.1 Resume API (기존)

```
POST /api/admin/traffic/batches/daily-usage-sync/{usageDate}/resume
```

- **대상 batch 상태**: `RUNNING`
- **동작**: 이미 RUNNING 중인 batch에 worker를 재개한다. batch row를 새로 만들지 않는다.
- **사용 시점**: worker 장애 후 동일 batch를 이어서 재개할 때.

### 4.2 Rerun API (신규)

```
POST /api/admin/traffic/batches/daily-usage-sync/{usageDate}/rerun
```

- **대상 batch 상태**: `FAILED` 또는 `ABANDONED`
- **`COMPLETED`에는 동작하지 않는다** (요청 거부).
- **동작 순서**:
  1. 해당 `usage_date`의 최신 batch 상태를 확인한다. `FAILED`/`ABANDONED`가 아니면 거부한다.
  2. 해당 `usage_date`의 `FAILED` target row 수를 집계한다.
  3. 새 `LINE_DAILY_USAGE_SYNC_BATCH` row를 생성한다.  
     (`target_count` = FAILED 개수, `status = RUNNING`)
  4. 해당 `usage_date`의 `FAILED` target row를 `RETRYABLE`로 전환한다.
  5. `LineDailyBatchWorkerScheduler.startForUsageDate(usageDate)`로 worker를 재개한다.
- `DONE`, `SKIPPED` target row는 건드리지 않는다. worker claim SQL 조건으로 자동 제외된다.

## 5. FAILED / ABANDONED 이후 Rerun 절차

### 5.1 Rerun 설계 원칙

- 이전 FAILED/ABANDONED batch row는 그대로 보존한다 (이력).
- **새 `LINE_DAILY_USAGE_SYNC_BATCH` row를 생성**하여 이번 rerun의 처리 결과를 독립적으로 집계한다.
- 새 batch의 `target_count` = 이전 run의 `FAILED` target row 개수.
- 이전 `DONE`/`SKIPPED` target row는 worker가 claim하지 않으므로 재처리되지 않는다.

### 5.2 Rerun 시 Count 흐름 예시

```
이전 FAILED batch:
  target_count=10,000 / success=7,000 / skipped=500 / failed=2,500
  status=FAILED  ← 이력으로 보존

        ↓ 운영자: POST .../rerun 호출

새 rerun batch (신규 생성):
  target_count=2,500   ← 이전 FAILED 개수
  success=0 / skipped=0 / failed=0
  status=RUNNING

LINE_DAILY_BATCH_TARGET 상태:
  DONE     7,000건 → 그대로 (claim 제외, DB insert 이미 완료)
  SKIPPED    500건 → 그대로 (claim 제외)
  RETRYABLE 2,500건 → worker가 선점하여 처리

완료 CAS (새 batch 기준):
  target_count(2,500) = success_count + failed_count + skipped_count
```

### 5.3 운영자 실행 절차

1. 장애 원인을 파악하고 수정한다.
2. Rerun API를 호출한다.
   ```
   POST /api/admin/traffic/batches/daily-usage-sync/{usageDate}/rerun
   ```
3. Discord 알림 또는 Prometheus를 통해 새 batch의 진행 상황을 모니터링한다.
4. rerun 완료 후 `failed_count > 0`이면 원인을 재확인하고 필요 시 다시 rerun한다.

## 6. COMPLETED Batch Rerun 금지 정책

### 6.1 원칙

`COMPLETED` 상태 batch의 rerun은 금지한다.  
Rerun API는 `COMPLETED` batch에 대해 요청을 거부한다.

### 6.2 금지 이유

사용량 테이블(`DAILY_TOTAL_DATA`, `DAILY_APP_TOTAL_DATA`, `FAMILY_SHARED_USAGE_DAILY`)은 **insert-only** 정책이다.  
COMPLETED 이후 재실행하면 동일 `usage_date + line_id` 조합의 duplicate key 오류가 발생한다.

### 6.3 예외 절차 (수동 작업)

COMPLETED batch의 데이터를 반드시 재처리해야 하는 경우, 아래 순서로 수동 작업 후 Rerun API를 호출한다.

> **주의**: COMPLETED → RUNNING 직접 상태 전환은 금지한다. 반드시 FAILED 경유 후 Rerun API를 사용한다.

```sql
-- Step 1. 사용량 테이블 row 수동 삭제
DELETE FROM DAILY_TOTAL_DATA WHERE usage_date = '?';
DELETE FROM DAILY_APP_TOTAL_DATA WHERE usage_date = '?';
DELETE FROM FAMILY_SHARED_USAGE_DAILY WHERE usage_date = '?';

-- Step 2. target row를 RETRYABLE로 수동 전환
UPDATE LINE_DAILY_BATCH_TARGET
SET status = 'RETRYABLE', status_updated_at = NOW(6)
WHERE usage_date = '?';

-- Step 3. COMPLETED batch row를 FAILED로 수동 전환
UPDATE LINE_DAILY_BATCH_JOB
SET status = 'FAILED', status_updated_at = NOW(6)
WHERE usage_date = '?'
  AND batch_name = 'LINE_DAILY_USAGE_SYNC_BATCH'
  AND status = 'COMPLETED';
```

```
-- Step 4. Rerun API 호출
POST /api/admin/traffic/batches/daily-usage-sync/{usageDate}/rerun
```

## 7. Resume API vs Rerun API 비교

| 항목 | Resume API | Rerun API |
|---|---|---|
| 엔드포인트 | `POST .../resume` | `POST .../rerun` |
| 대상 batch 상태 | `RUNNING` | `FAILED`, `ABANDONED` |
| batch row 생성 | 없음 | 새 row 생성 |
| target row 상태 전환 | 없음 | `FAILED` → `RETRYABLE` |
| worker 재개 | ✅ | ✅ |
| 사용 시점 | 동일 batch의 worker 장애 후 재개 | batch 자체 실패 후 재처리 |

## 8. 장애 판단 기준

| 상황 | 판단 기준 | 대응 |
|---|---|---|
| target row 처리 실패 | `failed_count > 0` → Discord 알림 | 로그 확인 후 원인 해소, rerun |
| deadline 초과 | 경과 시간 > 3시간 → Discord 알림 | 서버 상태 및 worker 로그 확인 |
| worker 무한 대기 | empty poll이 반복되며 non-terminal row 존재 | `PROCESSING` row lease timeout(1분) 대기 후 자동 재선점 여부 확인. 해소 안 되면 서버 재기동 후 resume |
| batch 미시작 | 06:00에 `LINE_DAILY_USAGE_SYNC_BATCH` 자체가 없음 | manager가 선출되지 않은 것. 서버 상태 및 Redis 확인 |
